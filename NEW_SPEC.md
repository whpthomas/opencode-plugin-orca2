# Workflow Specification

Workflow orchestrations are defined with TOML files. Each workflow comprises a sequence of steps with corresponding prompts. State is managed automatically by the generation and existence of output files -- artifacts created by each step, making workflows transparent, auditable, and resilient to process restarts. 

Workflows also support custom process configurations and multi-file task automation using generated artifacts to manage state across multi-step loops.

- `workflow/<workflow>.toml` Workflow definition
- `workflow/<workflow>/<step>.md` Workflow step prompts
- `process/<process>/<N>-<name>.md` Process prompts

## Invocation

Workflows are invoked as follows: `#{<workflow> <job> [<process>]}`

- `workflow` the workflow identifier
- `job` the inference job identifier, and
- `process` an optional inference process identifier

For example:

```txt
#{oct job-1 rms}
#{rpi 01-foundation}
```

### Project Types

There are currently two project types:

1. **Single-File Projects:** where each workflow job acts on a single input file. The job is contained inside sub-directory (using the filename slug) that encloses the input file along with the work artifacts generated by the job.
2. **Multi-File Projects:** where each workflow job acts on multiple project files and the job is contained inside the `thoughts` sub-directory inside that project working directory.

### Jobs

Jobs are uniquely identified self-contained directories that encapsulate the file based state machines of work artifacts generated by the agentic workflow inference.

- `<job>/` single-file project job directory
- `thoughts/<job>/` multi-file project job directory

### Processes

Processes allow workflow steps to be tailored to a specific process. For example you may have a OCR workflow containing `pdf2img` -> `transcribe` -> `extract` steps. A process could be used by the extraction step to specify a set of values to extract for a specific class of documents.

## Creating workflows

Workflows are created using toml files and markdown prompts in the `workflow/` directory.

For example the workflow definition:

- `workflow/rpi.toml`
- `workflow/rpi.md` workflow system prompt (optional)

Which might include the following steps:

```toml
description = "Simple research, plan and implement pipeline"
retry = 3

[[step]]
name = "research"
description = "Research the codebase"
prompt = [ "design-brief.md" ]
output = "research.md"

[[step]]
name = "plan"
description = "Create technical plan"
prompt = [ "design-brief.md", "research.md" ]
output = "plan.md"

[[step]]
name = "implement"
description = "Implement plan"
prompt = [ "design-brief.md", "plan.md", "research.md" ]
output = "report.md"
```

Along with corresponding step prompts

- `workflow/rpi/research.md` Research prompt implied by research step
- `workflow/rpi/plan.md` Plan prompt implied by plan step
- `workflow/rpi/implement.md` Implement prompt implied by implement step

Which might generate the following work artifacts:

- `thoughts/<job>/design-brief.md` User requested design brief prompt required by research input
- `thoughts/<job>/research.md` Codebase research artifact generated by research prompt inference
- `thoughts/<job>/plan.md` Technical plan artifact generated by plan prompt inference
- `thoughts/<job>/report.md` Implementation artifact report generated by implement prompt inference

## Creating workflow steps

Workflow steps are comprised of prompts, one for each step name, and are situated in the workflow directory.

- `workflow/<workflow>/<step>.md` Step prompt

### Step Prompt/Output Path Resolution

```toml
[[step]]
name = "plan"
description = "Create technical plan"
prompt = [ "prompt.md", "research.md" ]
output = "plan.md"
```

Input and output paths for multi-file projects:

- **prompt:** `thoughts/<job>/<step>.md` in the project directory (e.g. `thoughts/01-foundation/design-brief.md`)
- **output:** `thoughts/<job>/<step>.md` in the project directory (e.g. `thoughts/01-foundation/research.md`)

Input and output paths for single-file projects:

- **prompt:** `<job>/<step>.md` in the project directory (e.g. `Q1-report/document.md`)
- **output:** `<job>/<step>.md` in the project directory (e.g. `Q1-report/executive-summary.md`)

### Subtask Prompt/Input/Output Path Resolution

The `iterate` and `while` fields signify a file subtask step, where each input file inside the job sub-directory defined by `iterate` or `while` is processed by the workflow step in ascending order as a subtask.

- `$INPUT` the current subtask input path (e.g. `job-1/pdf2img/page-1.png`)
- `$OUTPUT` the current subtask output path (e.g. `job-1/transcribe/page-1.md`)
- `$INDEX` is a 1-indexed numeric sequence (e.g. 1, 2, 3 ... )
- `$EACH` is the name of each input file (e.g. `page-1`)

Prompt, input and output paths for single-file projects:

```toml
single_file = true
[[step]]
name = "transcribe"
description = "Transcribe '$EACH.png' page image to markdown content"
parallel = true
iterate = "pdf2img"
input = "pdf2img/$EACH.png"
prompt = [ "terms.md" ]
output = "$EACH.md"
concatenate = "doc.md"
```

- `step.iterate` relative to `<job>/<iterate>/*` in the project directory (e.g. `job-1/pdf2img/*`)
- `step.prompt` relative to `thoughts/<job>/` in the project directory (e.g. `thoughts/01-foundation/research.md`)
- `step.input` relative to `<job>/` in the project directory (e.g. `job-1/pdf2img/page-1.png`)
- `step.output` relative to `<job>/<step>/$EACH.md` in the project directory (e.g. `job-1/transcribe/page-1.md`)
- `step.concatenate` implicitly reads output directory files and concatenates them  (e.g. `job-1/doc.md`)

Prompt, input and output paths for multi-file projects:

```toml
[[step]]
name = "implement"
description = "Implement technical plan $INDEX"
iterate = "plan"
input = "plan/$EACH.md"
prompt = ["research.md", "design.md"]
output = "report-$INDEX.md"
```

- `step.iterate` relative to `thoughts/<job>/<iterate>/*` in the project directory (e.g. `thoughts/01-foundation/plan/*`)
- `step.prompt` relative to `thoughts/<job>/` in the project directory (e.g. `thoughts/01-foundation/research.md`)
- `step.input` relative to `thoughts/<job>/` in the project directory (e.g. `thoughts/01-foundation/plan/phase-1.md`)
- `step.output` relative to `thoughts/<job>/<step>/` in the project directory (e.g. `thoughts/01-foundation/implement/report-1.md`)

**Process Output Path Resolution:**

The `process` field signifies a process subtask step using the optional process argument, where each file inside the process directory is processed by the workflow step in ascending order as a subtask.

- `$OUTPUT` the current process subtask output path (e.g. `job-1/extract/date-of-contract.md`)
- `$PROCESS` is the user specified process identifier (e.g. `rms` invocation argument)
- `$EACH` is the name (slug) of each process file (e.g. `date-of-contract`)

```toml
single_file = true
[[step]]
name = "extract"
description = "Extract semantic data from content"
parallel = true
process = true
prompt = [ "doc.md" ]
output = "$EACH.md"
concatenate = "$PROCESS-extracted.md"
```

Input and output paths for single-file projects:

- `step.process` files located at `<project>/process/<process>/*` in the project working directory (e.g. `process/rms/date-of-contract.md`)
- `step.prompt` relative to `thoughts/<job>/` in the project directory (e.g. `job-1/doc.md`)
- `step.output` relative to `<job>/<step>/$EACH.md` in the project directory (e.g. `job-1/extract/date-of-contract.md`)
- `step.concatenate` implicitly reads output directory files and concatenates them (e.g. `job-1/rms-extracted.md`)

## Arguments

During each step: description field values, filename field values and the prompt content itself undergoes argument substitution using `$IDENTIFIER` syntax for each placeholder.

- `$PROJECT_PATH` the project working directory (e.g. `~/path/to/project`)
- `$JOB_PATH` the full job directory path (e.g. `thoughts/01-foundation` or `Q1-report`)
- `$JOB` the job identifier slug (e.g. `01-foundation` or `Q1-report`)
- `$WORKFLOW` the workflow identifier (e.g. `rpi`)
- `$PROCESS` the process identifier (e.g. `rms`)
- `$STEP` the current step identifier (e.g. `plan`)
- `$INPUT` the current subtask input path (e.g. `thoughts/01-foundation/plan/phase-1.md` for subtasks)
- `$OUTPUT` the current step output path (e.g. `thoughts/01-foundation/research.md` for steps and `thoughts/01-foundation/implement/report-1.md` for subtasks)
- `$EACH` the current subtask file name, excluding path and extension (e.g. `page-1`)
- `$INDEX` the current 1-indexed iteration number (e.g. 1, 2, 3 ... )

```markdown
# Example Task - Extract Semantic Data

You are tasked with finding and extracting semantic data from indexed document content as accurately as possible. Locate and extract the variables specified and write them as a markdown list to `$OUTPUT`. Identify the likely page number of the variables specified. Confirm the page number by reading the identified page located in `$JOB_PATH/transcribe/page-N.md`, where page number `N` = 1, 2, 3, ... etc.
```

### Iteration Arguments

Iteration steps generate multi-file outputs, where each input file inside the job sub-directory specified by `iterate` correlates to an output file to be generated. In this mode the orchestrator internally manages a subtask list, checking which output files are completed and halting when repeated failures exceed the retry count.

The `iterate` and `while` step fields provide `$EACH` and `$INDEX` placeholders for argument substitution, `$INPUT` comprises `<job>/<resolved.input>` and `$OUTPUT` comprises `<job>/<step>/<resolved.output>` path.

- `$INPUT` the current subtask input path (e.g. `thoughts/01-foundation/plan/phase-1.md`)
- `$OUTPUT` the current subtask output path (e.g. `thoughts/01-foundation/implement/report-1.md`)
- `$EACH` The current iteration filename, excluding path and extension (e.g. `phase-1`)
- `$INDEX` The current 1-indexed iteration number (e.g. `1`)

```toml
[[step]]
name = "implement"
description = "Implement technical plan $INDEX"
iterate = "plan"
input = "plan/$EACH.md"
prompt = ["research.md", "design.md"]
output = "report-$INDEX.md"
```

### While Loop Loops

While loops enable multi-file output to occur across multiple steps, where each file inside the job sub-directory specified by `while` correlates to an output file to be generated by each step. In this mode the orchestrator internally manages a subtask list for each step, however it is the loop step that checks if all while output files are completed for a given loop, halting when repeated failures exceed the retry count.

```toml
[[step]]
name = "implement"
description = "Implement technical plan $INDEX"
while = "plan"
input = "plan/$EACH.md"
prompt = [ "research.md", "design.md", "validate/fail-$INDEX.md" ]
output = "report-$INDEX.md"

[[step]]
name = "validate"
description = "Validate plan $INDEX implementation"
while = "plan"
input = "implement/report-$INDEX.md"
output = "pass-$INDEX.md"
loop = "implement"
```

In the above example, the workflow `implement.md` prompt would output `pass-1.md` if the subtask 1 passed, or `fail-1.md` if the success criteria was not met. The loop step would check `report-1.md` and `pass-1.md` exist before continuing to implement subtask 2 and so on.

### Process Arguments

The `process` step field also generates multi-file outputs, where each file inside the `process` directory correlates to an output file to be generated. In this mode the orchestrator internally manages a subtask list for the process step, checking which output files are completed and halting when repeated failures exceed the retry count.

- `$EACH` The current process filename, excluding path and extension (e.g. `date-of-contract`)
- `$PROCESS` The user specified process identifier (e.g. `rms`)
- `$INDEX` The current 1-indexed iteration number (e.g. `1`)

```toml
single_file = true
[[step]]
name = "extract"
description = "Extract semantic data from content"
parallel = true
process = true
prompt = [ "doc.md" ]
output = "$EACH.md"
concatenate = "$PROCESS-extracted.md"
```

## Toml Workflow Fields

Orchestrations are comprised of `toml` workflow files, and `markdown` step prompts. They expect the agent to generate output files, the existence of which provide the state mechanism for workflow orchestration.

### Workflow Format

The workflow implies a `workflow/<workflow>.md` system prompt, which if it exists is included as the system prompt.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `description` | string | Yes | Human-readable workflow description |
| `single_file` | boolean | No | Enable single file job mode (default: false) |
| `retry` | number | No | Max retries per step (default: 3) |
| `debug` | boolean | No | Enable verbose logging (default: false) |
| `stats` | boolean | No | Output a session statistics file (default: false) |
| `step` | array | Yes | Array of step definitions |

### Step Definition Syntax

Each step implies a `workflow/<workflow>/<step>.md` prompt included as the first user prompt. Steps prompts in the `input` list (if they exist) are only appended to the user prompt when this is the first step after the workflow is resumed. Parallel and subtask modifiers spawn independent child sessions that use the `input` list to build their prompts.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | Unique step identifier |
| `description` | string | Yes | Human-readable step description |
| `subtask` | boolean | No | Spawn subtask  (default: false) |
| `parallel` | boolean | No | Spawn parallel subtasks (default: false) |
| `process` | boolean | No | Run custom process configuration (default: false) |
| `dialog` | boolean | No | Pauses workflow with open-ended chat until output created |
| `retry` | number | No | Max retries for this step (overrides default retry) |
| `HITL` | boolean | No | Halt if retry count exceeded (default: false) |
| `generate` | boolean | No | This step generates an iterable set of files (default: false) |
| `iterate` | string | No | Iterate all files in specified subdirectory relative to job path |
| `while` | string | No | Iterate the next file in specified subdirectory across multiple steps |
| `loop` | string | No | Loop to target while output incomplete |
| `input` | string | No | Required input file path |
| `prompt` | string[] | No | Prompt file paths (accepts single string or array) |
| `output` | string | No | Required output file path |
| `concatenate` | string | No | Concatenate output on completion |

## State Machine

Steps have five state machine types, `step`, `generate`, `iterate`, `while` and `process`. There are also four modifiers, `dialog`, `subtask`, `parallel` and `loop`, which only work with specific state machine types.

Steps return one of four status responses:

- `RETRY` the required output was not generated
  - **Step or While:** inference should continue
  - **Iterate or Process:** inference should continue or if parallel re-spawn subtask
- `SUBTASK_DONE` the required output for subtask was generated
  - **Iterate or Process:** non-parallel should reset context and iterate subtask
  - **While:** should increment step or loop to target 
- `STEP_DONE` the required output for step was generated, increment step or workflow completed
- `HALT` the required output was not generated and retry count was exceeded
  - **Step or While:** halt workflow
  - **Iterate or Process:** halt workflow if `HITL` else continue

| Machine | Modifier   | Context | RETRY    | SUBTASK_DONE | STEP_DONE | HALT  |
|---------|------------|---------|----------|--------------|-----------|-------|
| Step    |            | parent  | continue |              | Next step | yes   |
| Step    | `subtask`  | child   | continue |              | Next step | HITL? |
| Step    | `dialog`   | parent  |          |              | Next step | pause |
| Generate|            | parent  | continue |              | Next step | yes   |
| Generate| `subtask`  | child   | continue |              | Next step | HITL? |
| Iterate |            | parent  | continue | Next Subtask | Next step | yes   |
| Iterate | `subtask`  | child   | continue | Next Subtask | Next step | HITL? |
| Iterate | `parallel` | child   | re-spawn |              | Next step | HITL? |
| While   |            | parent  | continue | Next step    | Next step | yes   |
| While   | `subtask`  | child   | continue | Next step    | Next step | HITL? |
| While   | `loop`     | -       | -        | Loop step    | -         | -     |
| Process |            | parent  | continue | Next Subtask | Next step | yes   |
| Process | `subtask`  | child   | continue | Next Subtask | Next step | HITL? |
| Process | `parallel` | child   | re-spawn |              | Next step | HITL? |

### Context window Behavior

By default, steps are inferenced sequentially within the main context window. A combination of the step prompt, subtask input, and prompts provide the full context for each step or subtask. As teh workflow progresses, only step prompts from subsequent steps and or input prompts from subsequent are included in the main context window.  However if the workflow resumes, the current step rebuilds the full prompt before it continues. Parallel and subtask modifiers spawn independent child sessions that each build full prompts.

### Dialog Steps

The `dialog` field enables open-ended chat with the user. The workflow pauses (session remains alive) and waits for the user to respond to questions. This is useful for:

- Requirements gathering sessions
- User interviews and feedback
- Collaborative planning
- Any scenario requiring extended human interaction

**Example:**

```toml
[[step]]
name = "design"
description = "Design alignment"
sequential = true
dialog = true
prompt = ["prompt.md", "research.md"]
output = "design.md"
```

**What happens:**

1. Workflow reaches the dialog step and sends the initial prompt
2. Workflow pauses - no automatic retries occur
3. User can chat normally with the agent
4. When the output file is created, workflow automatically resumes
5. Next step proceeds normally

### Error Handling

If expected output is missing after max retries, the workflow halts. This requires human intervention.

**Automatic resume on re-invocation:**

When a workflow is re-invoked, it walks backwards through the steps to find the last complete step. If a step is found complete, the workflow resumes on the step after it. If no step is found complete, the workflow restarts from the first step. This allows users to:

- Manually create missing output files to skip failed steps
- Fix the underlying issue and re-invoke without losing progress
- Create partial outputs to control which steps execute

To recover:

1. Check the error log
2. Manually create missing output files OR
3. Fix the issue and re-invoke the workflow
